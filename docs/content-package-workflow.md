# 统一稿件包与 Halo 接收流程

日期：2026年10月14日，2026年10月17日更新媒体与运营。用途：记录四模块的内容交付方式，供未来 Codex skills、Halo 插件和主题适配参考。术语见[内容术语](../CONTEXT.md)，来源选择见[数据源调研](./cms-data-source-research.md)。统一接收、原生入口与完整版本保护已部署；[私有 S3 媒体、撤稿归档与历史恢复](./cms-media-operations.md)已接入，CDN 尚未实施。完整包格式、样例与限制以[协议 1.0](../demo/halo-poc/contracts/README.md)为准。

## 已确认范围与技术建议

用户确认的工作方式：Codex 通过 skills 完成链接内容获取、多文件整理、Word/Markdown 转换、标题摘要结论生成，以及标准稿件包交付。首版 Halo 自动化插件只有一个稿件包接收入口，负责校验、生成草稿、预览、人工审核和发布。网站图片与附件计划走对象存储，公开访问计划接入 CDN。

建议四模块共用交付协议与审核流程，正文用 Markdown，结构化业务数据用 JSON。沿用 Halo 和现有 PostgreSQL 管理修订及发布状态；公开 HTML/JSON 由发布版本派生，供缓存/CDN 分发。首版不增加 Elasticsearch。字段、请求路径与资源上限已冻结并验证；CDN 失效策略仍待实现与验证。

## 分工与内容流转

```mermaid
flowchart LR
    I[测评链接或作者文件] --> C[Codex 与 skills]
    C --> B[统一稿件包]
    B --> R[Halo 插件接收与校验]
    R --> D[完整草稿与网页预览]
    D --> H[人工审核和修改]
    H --> P[明确发布版本]
    P --> O[公开 HTML 与 JSON]
    O --> CDN[缓存与 CDN]
```

Codex 侧负责内容生产，插件负责网站管理。插件不包含网页采集器、Word 转换器、AI 模型调用或三种独立生成界面。文章预览、审核、发布、任务查询与公开读取仍有后台常规接口；“一个接收入口”指一个自动化内容提交接口，不是把全部操作混进一个免鉴权接口。

生产任务不放在访客请求中。Codex 可以先在本机产出并留存稿件包，再调用接收接口；因此首版不依赖 Halo 容器能访问所有外部内容源，也不会因某个测评站点失效而阻塞访客。

## 四模块如何统一

一个稿件包对应一个可单独审核与发布的内容条目。共用包的外层字段，按 `kind` 校验不同的 `data` 结构；统一交付和管理，保留各模块自己的数据含义。

| kind | 一个包的范围 | Markdown 正文 | JSON 业务数据 |
|---|---|---|---|
| review | 一份测评摘要或本站测评 | 测试对象、发现、结论、限制及原文入口 | 任务、工具/型号、来源、结论证据和关联信息 |
| tutorial | 一篇教程 | 前置条件、步骤、提示词、示例、常见问题 | 适用工具/版本、任务、附件、复现时间和核验状态 |
| leaderboard | 一份任务与口径确定的榜单快照 | 评分方法、范围、推荐说明；可选 | 条目 ID、型号、原始成绩/单位、排序或权重规则、来源和时间 |
| pricing | 一个产品的价格方案集合 | 权益解释、选择建议与实测说明；可选 | 方案 ID、金额/币种、地区/渠道、周期、免费额度、限制和核验时间 |

评分、价格、名次与筛选字段以 JSON 为准，由页面生成表格和对比。不要同时人工维护 Markdown 价格表和 JSON 价格记录；需要导出表格时由 JSON 生成。不同评分体系、币种、计费单位和会员/API 渠道分别保留，不能因包格式统一就混合排序。

价格包中的每个方案、榜单中的每个条目有稳定 ID。不要每次更新整站数据：按产品、榜单或文章拆包，可以单独审核、更新与回滚。多条记录可以属于同一个包，但首版不承诺跨多个包的原子发布。

## 稿件包 1.0

本地可保存为 `manifest.json`、`body.md`、`data.json`；图片附件单独上传并在清单中引用。提交时由 skill 或其脚本读取这些文件，合并为一个 JSON 请求。首版不需要 ZIP 上传、解压或在 JSON 内传图片 Base64。

| 字段 | 含义及约束 |
|---|---|
| schema_version | 交付格式版本；插件只接受明确支持的版本 |
| content_id | 内容条目稳定 ID；更新沿用，不能每次重跑都新建 |
| submission_id | 本次交付 ID；同包重试沿用，新内容修订使用新 ID |
| kind | review、tutorial、leaderboard、pricing |
| base_revision | 更新所基于的后台修订标识；更新必须提交，过期则产生冲突 |
| content | title、summary、body_markdown、分类/标签和必要的公开说明；榜单/价格正文可为空 |
| data | 按 kind 定义的业务字段；不能用任意自由文本替代必要的结构化数据 |
| sources | 来源 ID、URL、作者、原文日期、获取时间、使用范围及证据定位 |
| assets | 附件 ID、对象标识、类型、校验和、说明和访问属性 |
| provenance | 生成 skill 及版本、生成时间、输入材料哈希等；未知信息不编造 |

完整可提交样例：[测评](../demo/halo-poc/package-fixtures/review.json)、[教程](../demo/halo-poc/package-fixtures/tutorial.json)、[榜单](../demo/halo-poc/package-fixtures/leaderboard.json)、[价格](../demo/halo-poc/package-fixtures/pricing.json)。四者共用一个严格 JSON Schema，未知字段一律拒绝；示例均为虚构。旧的最小示意已由这些完整样例替代。

`base_revision` 在新建时省略，在更新时使用接收回执中的有效值。状态、审核人、发布时间、公开 URL 和服务器修订号由服务端维护；包内即使带有“已发布”字样也不能取得发布权限。接收时拒绝未定义字段，规则在 Schema 中固定。

附件优先保存稳定对象标识，不把会到期的签名 URL 或固定 CDN 域名当作唯一地址；由网站映射访问 URL。外部原视频链接仍是来源引用，不强制变成本网站对象。原始 Word/Markdown 和允许保存的来源材料可放私有归档，与公开媒体分开。

## 一个接收入口的行为

实际入口为 `POST /apis/console.api.aihyb.run/v1alpha1/content-packages`。Codex 使用只允许提交草稿的身份提交 JSON；当前经 SSH 隧道访问仅监听服务器本机的 HTTP，正式域名部署时接 HTTPS。首版先同步完成小包校验和草稿保存，返回内容 ID、草稿修订、处理结果和需要登录的预览地址；若渲染改为异步，再返回任务 ID 与查询地址。

接收校验依次检查支持的格式版本、包大小和基本字段、kind 对应业务结构、来源与附件引用、记录 ID 和数值口径、更新版本与重复提交，最后创建完整草稿。错误返回具体字段路径与原因，便于 skill 修正；收到请求不等于稿件已经保存成功。

已实现的幂等规则为同一自动化身份下的 `submission_id` 与服务端计算的请求内容哈希配对：同 ID 同内容重试返回原结果，同 ID 不同内容拒绝。服务端保留请求摘要与处理状态，中断后可对账；不能只在客户端去重。哈希不依赖 JSON 空白或键顺序，规范化方法在客户端/服务端契约中固定。

例如，运营已经修订标题，Codex 又提交基于旧草稿的版本，应拒绝更新并返回冲突，不能覆盖运营修改。重复提交已发布条目的相同包，也不能退回旧草稿、撤销发布或再次重复创建。单个包采用整体替换草稿的语义，首版避免含糊的字段自动合并。

## 预览审核与发布隔离

编辑可以查看原始来源、生成稿、完整结构化数据、校验错误及真实网页预览；自动修订差异视图尚未实现。外部测评摘要需清楚标注出处并提供完整原文入口；教程需核对步骤、提示词、附件和适用版本。修订后保留操作者和版本记录。

审核绑定明确的修订与内容哈希。审核后若正文、标题、数据或附件发生改变，必须审核新修订；发布接口检查期望修订及当前权限。公众页面、列表、SEO、筛选与比较都读取同一完整发布版本。保存或导入新草稿不切换公开内容，不更新公开缓存。

已按用户确认改为“原生文章入口＋少量稿件扩展＋完整版本保护”。审核人员从 Halo 文章列表进入，在原生编辑器保存标题、摘要及 Markdown；文章操作和编辑器中的“稿件数据与审核”打开来源、结构化记录及批准面板，审核后使用原生发布按钮。独立稿件列表菜单已移除。详细实现和验证见[原生适配记录](./cms-native-adapter.md)。[Halo 自定义模型](https://docs.halo.run/developer-guide/plugin/api-reference/server/extension)、[内容参数](https://github.com/halo-dev/halo/blob/v2.26.1/application/src/main/java/run/halo/app/content/ContentUpdateParam.java)

ContentRevision 保存完整不可变包及渲染哈希；受管理的原生 Post 是草稿、批准、发布及幂等日志的唯一状态权威。Post 的公开标题、摘要、releaseSnapshot 和 JSON 发布修订在同一次带版本校验的更新中切换。ContentEntry 仅保留稳定内容 ID 与模块注册，旧指针不再作为可写主数据。私有编辑响应显示新标题，公开 Post 保留已发布标题；保存新稿清除批准。外部原始修订写入禁用，受管理文章写入经过适配服务。跨包联动发布以后单独设计。

## 存储与 CDN 的职责

| 内容 | 推荐存放位置 | 说明 |
|---|---|---|
| 当前草稿、发布版本、审核记录、来源、元数据、Markdown 与 JSON | Halo 插件资源，持久化到现有 PostgreSQL | 首版通过 Halo 官方客户端访问，保持唯一可写权威数据 |
| 图片、视频和附件 | 对象存储 | 数据记录保存对象标识与访问属性；保密稿件附件私有 |
| 原始交付包及允许保存的输入文件 | 私有文件归档或对象存储 | 保留原始字节便于审计/重放，按保留策略管理；归档不是第二个可编辑主库 |
| 已发布 HTML、公开 JSON 和筛选读模型 | 缓存，必要时输出到对象存储供 CDN 读取 | 可以从发布版本重建；不放草稿、审核意见或自动化凭据 |
| 全文搜索索引 | 未来按需求考虑 Elasticsearch | 只索引公开发布版本，作为可重建派生数据 |

Markdown 可以作为文本保存，JSON 也可以保存在 PostgreSQL；独立业务表的 JSONB 有查询与索引能力。但 Halo 自定义资源不等于可以直接设计它的内部表或任意建立 JSONB SQL 索引，首版使用它的资源客户端与实际字段索引。只有未来外置业务服务时才单独决定 text/JSONB 表结构。[PostgreSQL JSON 类型](https://www.postgresql.org/docs/17/datatype-json.html)、[Halo 资源客户端](https://docs.halo.run/developer-guide/plugin/api-reference/server/extension-client)

Elasticsearch 能存文档，但首版的主要问题是草稿版本、审核、发布隔离及基础筛选；新增 ES 仍需实现这些管理规则，并承担索引、备份与同步维护。当前已有 PostgreSQL，先复用它。如果中文全文搜索、相关性排序或大规模搜索聚合确有需求，再从已发布版本建立 ES 索引。ES 搜索的可见性还受 refresh 影响，不能默认它与审核发布瞬时同步。[Elastic 搜索可见性说明](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)

CDN 加速公开读取，不管理审核状态。版本化 HTML/JSON 只有在批准发布后才生成公开制品；更新先准备完整制品再切换版本引用，失败保留旧版，失效刷新可重试。跨 CDN 节点的更新不是全球瞬时原子切换，需约定可接受的旧版缓存窗口；单个页面所用数据引用应固定到同一发布版本。

后台、登录预览、接收回执和任务状态不进入公共缓存。草稿素材用私有对象和经过授权的访问方式，不能因为文章没发布就假定 CDN 上的附件也是私密。对象存储版本化与 CDN 均不替代数据库及对象的备份恢复。

## 未来 skills 应保留的规则

1. 输入允许链接、Markdown、Word 和多文件；先确定性解析内容与附件，再由 AI 整理，不要求作者使用固定输入格式。Word 首版以 DOCX 为主，旧 DOC 另行转换。转换保留结构，不承诺恢复原排版；复杂表格和图片说明进入检查清单。[Pandoc 转换说明](https://pandoc.org/MANUAL.html)
2. 原始内容、标准稿件与网站发布版本分别保留。明确材料之间的来源关系，不能把标准化成功当成结论验证成功。
3. 外部测评生成标题、摘要、发现、结论与限制，重要判断关联原文证据；无法取得正文时请求补充，不凭标题补写实测。
4. 原链接、作者和来源日期由提取与校验步骤填入。测评页面带明显原文入口，区分原作者观点、本站补充和原创实测。
5. 教程保留输入稿中的命令、参数、提示词和文件对应关系；AI 新增的步骤或实测说法标为待核验，保留人工复现环节。
6. 价格和评分中的未知值用 null 或明确状态表示，不能生成 0；金额、单位、地区、渠道、基准及版本必须校验。同一基础数据不同时手工维护两份表。
7. 图片和附件先取得稳定引用；未经核验的外部 HTML/脚本不作为可执行页面内容。Markdown 方言与扩展固定，表格、代码、脚注和视频组件的渲染以预览为准。
8. skill 只生成包、校验包并提交草稿；网络重试沿用交付 ID，内容条目 ID 保持稳定。获取接收回执并报告成功、校验失败或版本冲突，不能把 HTTP 连接成功当成完成导入。
9. 人工修改后重新生成必须基于当前修订。审核与发布由后台执行；模型建议的 publish/status 字段不构成发布指令。
10. 包格式、各 kind 的 JSON Schema、示例、提交脚本和回执约定应共用同一版本。未来新增 skill 复用这些协议，避免每个 skill 自定义字段。生成 skill 与提交能力可分别维护，但首版不必拆成很多技能。

## 首版实现与验证边界

四种包的 Schema 与虚构样例、单接收入口、回执、完整草稿、修订绑定预览和审核发布已完成。已实现模块/任务基础筛选、结构化表格与包内价格对比；跨产品聚合比较、发布缓存、主题适配和媒体组件继续按 PoC 推进。Codex skills 只需要能够产出并提交这些样例，就能独立推进内容生产。此处记录未来技能要求，不创建或安装 skill。

验收重点：四种包通过同一入口入草稿；错误字段可定位；同包重试不重复；后台人工修改不被旧包覆盖；重跑 AI 不影响已发布页；标题、摘要、正文和结构化数据同时隔离；审核后再修改不能误发布；草稿不进入 CDN；价格/评分来自 JSON；备份恢复同时恢复发布版与草稿版。大型包、关联缺失及附件失效时不能半包发布。性能测试沿用低强度 PoC，不改变既有服务。

当前限制：Markdown 原始 HTML 转义，专用视频嵌入组件尚未接入；附件引用可以进入草稿，但对象完整性和访问控制就绪前禁止非空 assets 发布。后台暂没有修订历史列表、定时发布或撤稿按钮。完整验收状态见[PoC 执行记录](./cms-poc-progress.md)。
